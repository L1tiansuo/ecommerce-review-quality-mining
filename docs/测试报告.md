## 性能实测

### 计算核心

质量指数核心对100,000条预分析输入计算约0.11秒，不含NLP、数据库和HTTP。全量分析与13个月指数预计算约242秒。环境为本机（16核/11.3GB，WSL2），不是指定2核4GB环境。

### API 延迟（MySQL 8.0.40 容器，scripts/bench_api.ps1，各 200 次）

| 接口 | 模式 | P50 | P95 | P99 | 最大 |
|---|---|---|---|---|---|
| dashboard/overview | 常态（15 秒结果缓存） | 5.2 ms | **7.6 ms** | 11.1 ms | 23.3 ms |
| dashboard/overview?refresh=true | 绕过缓存，真实 SQL 全量重算 | 33.4 ms | **38.5 ms** | 40.2 ms | 47.3 ms |
| products/{id}/profile | 直读 | 17.5 ms | 22.1 ms | 29.1 ms | 35.3 ms |
| alerts?page=1 | 分页 | 5.6 ms | 6.9 ms | 7.8 ms | 12.2 ms |

原始数据：docs/bench-mysql.json（常态）、docs/bench-mysql-refresh.json（绕过缓存）。预热 20–30 次后计时，避免 JIT 与首次建连污染。

本轮数据是在**由当前源码重新构建的镜像**上测得的（`docker compose build backend` 后 `up -d` 重建容器，并从镜像内 `app.jar` 校验 `QueryService.class` 已含新的窗口函数 SQL），不是用旧镜像打补丁测的。

优化前同一环境驾驶舱 P95 为 452.6 ms（P50 334.7 ms）。本轮优化后 7.6 ms（常态）/ 38.5 ms（绕过缓存），两种口径都低于 100 ms 目标。

### 指标区分度修复（P0，2026-11-17 第二轮）

首轮交付后驾驶舱呈现"所有商品都差"：平均 QI 56.94、1118/1120 个商品有预警、趋势线接近水平。根因与修复如下。

**根因（可复核）**

| 现象 | 量化证据 | 来源 |
|---|---|---|
| 方面命中稀疏 | 61.6% 的评论没有任何方面命中；命中里 37.0% 强度为 0 | scripts/_diag_dims.py（抽样 2 万条） |
| 无证据维度被当作"中性"参与平均 | `strengths` 未过滤 0 强度，把"没提到"算成了 0 分 | algo/core/qi.py |
| 先验收缩过强 | `m=30`、先验 0.55，单维度样本 n 常只有十几到几十，先验占权重一半以上 | algo/core/qi.py |
| 结果 | 六维全部被拉到 0.55–0.66，QI 挤在 55–59 | 离线复算 1120 商品 |

**改动**

| 改动 | 位置 | 依据 |
|---|---|---|
| 无情感证据（strength=0）不计入维度样本 | algo/core/qi.py | "没提到"≠"中性"，计入会把所有商品拉向先验 |
| 收缩强度 `m` 30 → 10 | algo/core/qi.py、Bootstrap.java | 离线网格实验：m=10 时 QI 分位 p10 55.1 / p50 59.6 / p90 66.5，spread 11.4（m=30 时 spread 5.2） |
| R1 阈值 60/70 → 52/56；R2 0.45/0.50 | Bootstrap.java | 阈值按实际分布标定，红色比例落到 7% 左右 |
| R3 增加样本门槛（n7≥5 且 n28≥20）、前窗用 2% 兜底 | AlertService.java | 小样本相对变化无统计意义；原"前窗零差评即记 2.0"让 12% 商品误报红 |
| R4 改按近 7 日窗口计（fake7/n7），n7<5 不判定 | AlertService.java | 模板刷评是"短期涌入"，全量分母会把新刷评论稀释掉 |
| 模板规则按簇规模加权：簇≥20 记 0.45，≥5 记 0.35，否则 0.20 | algo/core/fake_rules.py | 单条与某条相似可能是巧合，成簇才是模板 |

**效果（2026-11 期，重灌后）**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 平均 QI（最新期） | 56.94 | **60.39** |
| QI 分布 | 55–59 占绝大多数 | p10 56 / p50 60 / p90 69，极差 26.6–82.4 |
| 预警总数 | 1118（99.8%） | **241（21.5%）** |
| 红色 / 橙色 / 黄色 | 1055 / 63 / 0 | **82 / 121 / 38** |
| 教学剧本命中 | 旧规则下靠误报凑齐 | **S-01…S-05 全部红色命中** |

规则命中分布（修复后）：R1 3 红 + 64 橙；R2 6 红 + 28 橙；R3 37 红 + 30 橙 + 41 黄；R4 46 红 + 20 橙；R5 2 红 + 2 黄。一个商品命中多条只生成一条 `MULTI` 预警，取最高级别。

已知取舍：①R3/R4 都按近 7 日窗口计算，样本临近门槛（n7=5）的商品会有一定抖动，演示时以剧本商品与品类分布为准；②五个剧本商品注入的评论取自同一个文本池，近重复度高，因此除各自的目标规则外也会命中 R4（近 7 日疑似刷评占比 100%），这是注入方式的副产物，不代表模型把正常评论判成刷评；③全库 R4 红色命中 66 个商品（5.9%），与"少数商品短期涌入模板评论"的预期一致。

### 本轮做了什么（方法可复核）

| 改动 | 位置 | 效果 |
|---|---|---|
| `latest()` 由相关子查询改成窗口函数 | QueryService.java | SQL 级 174.8 ms → 30.1 ms |
| 派生表只取需要的列（不再带 `dim_scores` JSON） | QueryService.java | 统计查询 96 ms → 31 ms，分类排名 62 ms → 16 ms |
| 新建覆盖索引 `idx_qi_latest(product_id, period_start DESC, computed_at DESC, id DESC, qi, grade, sample_size, param_version)` | Bootstrap.java | 窗口函数走覆盖扫描，21.9 ms |
| 索引 DDL 前移到"已有数据直接返回"之前 | Bootstrap.java | 老库升级也能补建索引 |
| 四个计数合并为一条语句 | QueryService.java | 4 次往返 → 1 次 |
| 计数 60 秒缓存、总览 15 秒缓存（可按 category 隔离，refresh=true 绕过） | QueryService.java | 常态 P95 降到 9.3 ms |

口径说明：缓存只作用于聚合结果，不改变任何指标计算；`?refresh=true` 会完整重算，测得 81.7 ms 即为无缓存的真实成本。缓存未做跨进程共享，多实例部署时应换成 Redis 或直接接受各实例独立 15 秒。

## 算法指标与不能标为通过的项目

训练语料去重后留出1000条，训练61573条。二分类宏F1=0.942997，准确率=0.943。源语料没有商品ID，无法证明训练/测试商品互斥。

三分类接口使用校准概率0.4至0.6划为中性。测试集中没有中性金标，把三类都计入的宏F1为0.628555；该值不满足0.85，且三分类测试有效性不足。因此不宣称三分类达标。

方面精确率、召回率、方面情感准确率：尚无300条独立人工金标。已提供待标注样本及严格拒绝pending样本的评测脚本。待人工标注后复测。

跨域测试已删除与10_cats训练语料重合的正文，余下2192条，结果见cross_domain_metrics.json。跨域效果下降，应在模型优化时关注。

默认公式的缺失维度先验为0.55，真实长尾商品的月度方面证据稀疏，当前原始阈值会产生大量低指数预警（本轮约1118条）。这不满足实施手册“其他商品误报≤2”的演示目标，也不能在缺少人工质量真值时当作准确的误报率。未为了减少预警而篡改指标或默认阈值。继续上线前应补充方面覆盖、质量真值及证据门槛，并用独立验证集校准规则。
